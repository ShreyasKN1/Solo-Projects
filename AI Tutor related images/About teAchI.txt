Why Most AI Applications Fail

Most AI applications fail not because of the model, but because of the system built around it.

Large Language Models are powerful, but by nature they are:

Stateless –> they do not remember past interactions

Non-deterministic –> the same input can produce different outputs

Because of this, calling an LLM directly is never sufficient for building a reliable AI system.

Design:

In teAchI, the LLM is treated as a language generation layer, not as a source of truth.

Reliability comes from architecture, not from trusting the model.

How teAchI Works
1) Knowledge Retrieval (RAG)
Curated, domain-controlled knowledge is retrieved before generation.
This grounds responses and prevents the model from hallucinating beyond known context.

2) Prompt Assembly with Constraints

The system prompt injects:

->Retrieved context

->Learning level (Beginner ->Intermediate-> Advanced)

->Token limits

->Explanation style constraints

This ensures the model reasons within boundaries.

3) LLM Generation (Stateless)

The LLM generates an answer using:

->No memory

->No correctness awareness

->No evaluation capability

This is expected and intentional.

=> Post-Response Evaluation (Service Layer)

After the response is generated, it is evaluated using a dedicated EvaluationService.

⚠️ Important correction(Change in design):
Spring AI Advisors do NOT intercept final LLM responses in stable versions.
They operate at the prompt construction stage, not at response evaluation.

Therefore:

Advisors are used for control

Evaluation is done after the call, in a service layer only

This design is deliberate and correct.

What Is Evaluated After Each Response

Every response is evaluated per request using heuristics that reflect real-world uncertainty.

🔹 Groundedness (0.85 vs 0.6)

Exact grounding is difficult -> overlap ≠ correctness

Context overlap is still a strong signal

0.85 = likely grounded, but not verified truth

Not 1.0 -> LLMs paraphrase

Not 0.7 -> overlap is stronger than average

Fallback 0.6 -> answer may be correct, but grounding is uncertain

Outcome:
Prevents false confidence and avoids overstating reliability.

🔹 Explanation Quality (0.9 vs 0.5)

Signals used:

Answer length (>100 chars → completeness)

Reasoning markers (“because”, “step”, “therefore”)

0.9 = structured, educational explanation

Not perfect -> heuristic, not semantic understanding

Fallback 0.5 -> short answers may be correct but weak educationally

Outcome:
Balances verbosity vs usefulness.

Verbose ≠ good. Concise ≠ bad.

🔹 Retrieval Quality (default 0.4)

Default 0.4 intentionally signals uncertainty

Below “usable” threshold by design

Forces attention on KB quality

Not 0.0 -> partial recovery possible

Not 0.6 -> would hide retrieval issues

Outcome:
Retrieval failures are visible, not silent.





System Flow (Corrected changed advisors as we can't intercept response)
User Question
   ↓
Knowledge Retrieval (RAG)
   ↓
Prompt Assembly (Context + Level + Constraints)
   ↓
LLM Generation (Stateless)
   ↓
Post-Response Evaluation (Service Layer)
   ↓
Response Returned




Why This Matters in my project:

LLMs do not know if their answers are good.

Reliability comes from:

Grounding (RAG)

Adaptability (learning levels)

Control (Advisors)

Validation (evaluation services)

Same model.
Same knowledge.
Different constraints -> different learning experiences.

AI systems don’t become reliable because models improve.
