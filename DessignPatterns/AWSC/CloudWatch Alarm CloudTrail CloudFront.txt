=> CloudWatch Alarm for EC2

Open AWS Console -> CloudWatch.
Go to Alarms -> All alarms.
Click Create alarm.
Click Select metric.

Select either,
EC2
Per-Instance Metrics
Select your EC2 instance.

Choose a metric, for example:
CPUUtilization
Configure/ similar to .ebextensions remember:
Statistic: Average
Period: 5 minutes
Threshold: >= 80%
Evaluation periods: 1 or 2

Under Notification,

 choose/create an SNS topic.
Add your email subscription if required.
Give the alarm a name like
EC2-High-CPU


Click Create alarm.

CloudWatch can monitor EC2 metrics automatically, and the alarm can publish to SNS when the threshold is breached.

For a production application, create additional alarms for:

CPUUtilization-> main
StatusCheckFailed
NetworkIn / NetworkOut
EBS volume metrics
Application 5xx errors-> main
Request latency




=> CloudTrail

CloudTrail is for auditing AWS API activity like who created/deleted/modified resources, IAM changes, security-group changes, etc.

Create the trail
Open AWS Console -> CloudTrail.

Go to Trails.
Click Create trail.

Give it a name:
production-audit-trail


Under Storage service,

Choose Create new S3 bucket
Or select an existing dedicated logging bucket.

Enable multi-Region trail=> when we use console created trails always enabled.

Keep management events enabled.

Configure data events only if you specifically need them.

Enable log-file validation if required.

Enable encryption as appropriate.

Click Create trail.

Check that Logging = On for it.

AWS recommends multi-Region trails because they capture activity across enabled Regions.

Good architecture:

 CloudTrail -> CloudWatch

If you want an alarm for something like:

Someone changed a security group
Someone changed an IAM policy


then:

Send CloudTrail events to CloudWatch Logs.
Create a CloudWatch metric filter.
Create a CloudWatch alarm on that metric.
Send the alarm to SNS.



=> CloudFront:

Connect existing EC2 application to CloudFront

Your current architecture is roughly:

User
->
EC2
->
Spring Boot

We want:

                          ┌── Cache HIT -> Static/Dynamic response
                        │
User -> CloudFront ───┤
                        │
                          └── Cache MISS -> EC2 -> Spring Boot-> DB.

CloudFront can use an EC2-hosted HTTP server as a custom origin.

First,
-> Make EC2 reachable as an origin
Open EC2 -> Security Groups
Ensure the EC2 security group allows the required HTTP/HTTPS traffic.
Make sure your Spring Boot application is listening on the required port.

For example:
Spring Boot
port = 8080

Ideally, never expose 8080 directly to users.


-> Create CloudFront distribution
Open AWS Console → CloudFront.
Click Create distribution.
Under Origin enter your EC2 origin.
EC2 public DNS / hostname



->Configure the origin protocol:
Prefer HTTPS for production.
->Configure the viewer protocol:
Redirect HTTP to HTTPS.
->Configure allowed methods.

For a normal web application it would be like,
GET
HEAD
OPTIONS

For APIs requiring writes:
GET
HEAD
OPTIONS
PUT
POST
PATCH
DELETE

CloudFront supports these methods, but non-GET/HEAD requests aren't cached like normal GET/HEAD content.


CloudFront and handling static/ dynamic contents:


=> Configure static content caching

Suppose your Spring Boot app has:

/static/*
/images/*
/css/*
/js/*

Create CloudFront cache behaviors such as:

/images/*
/css/*
/js/*

For these:

Cache = enabled
TTL = relatively long

CloudFront serves these from edge locations.
Cache determine which origin and caching rules apply to matching paths.

=>  Configure dynamic API content

For:

/api/*

create another CloudFront behavior.

Configure:

Path pattern:
 /api/*

Origin:
 EC2

Allowed methods:
 GET
 POST
 PUT
 PATCH
 DELETE
 OPTIONS

Caching:
 Disabled / very low TTL

CloudFront still gives you benefits such as a nearby TLS endpoint and edge routing, but you generally don't want personalized API responses cached accidentally.

=> Add your domain

If your application/site exists on:

example.com

then:

Open AWS Certificate Manager (ACM).
Request a certificate for:
example.com
www.example.com
Validate ownership.
Attach the certificate to CloudFront.
In Route 53, create/update your DNS record.
Point:
example.com
        ->
CloudFront distribution

Now:

User
->
example.com
 ->
Route 53->
CloudFront nearest edge
->
EC2 origin



Important to remember that,
don't blindly cache dynamic content

Use:

Static files =>  aggressive caching
Public immutable API =>  potentially cache
Personalized API =>  don't cache
POST/PUT/DELETE =>  don't cache

For example:

GET /images/logo.png
        ->
CloudFront cache

GET /products
        ->
Could cache depending on requirements
