Outbox Pattern System Design:

The Outbox Pattern is used to achieve reliable event publishing in distributed systems where a service needs to update its database and publish an event to a message broker like Kafka. Instead of trying to perform both operations atomically, which isn't possible with a normal database transaction, the service writes the business data (for example, an Order) and an Outbox event into the same database transaction. This guarantees that either both records are committed or both are rolled back. A separate background publisher continuously polls the Outbox table for pending events, publishes them to Kafka, and then marks them as sent. If the publisher crashes after Kafka acknowledges the message but before updating the Outbox row, the event may be published again after restart.

The Outbox Pattern provides at-least-once delivery, not exactly-once delivery. Reliability comes from storing the event in the database first, while correctness comes from idempotent consumers that safely handle duplicate events.

1. DB Commit successful but Kafka Publish failed
Issue: Order is saved but other services never receive the event.
Fix: Save both the Order and Outbox event in the same DB transaction. A background publisher retries publishing later.

2. Publisher crashes after publishing to Kafka
Issue: Event reaches Kafka, but Outbox status remains PENDING, so it gets published again after restart.
Fix: Consumers should be idempotent (track eventId in a processed_events table and ignore duplicates).

3. Multiple publisher instances
Issue: Two publishers read the same Outbox row and both publish it.
Fix: Use row locking (FOR UPDATE SKIP LOCKED) or update the row to PROCESSING before publishing.

4.Kafka is unavailable
Issue: Events remain in the Outbox.
Fix: Retry with exponential backoff. Move permanently failed events to a DLQ or mark them as FAILED.

5.Outbox table keeps growing
Issue: Millions of processed events impact performance.
Fix: Periodically archive or delete SENT events and index the status column.

6.Kafka unavailable for a long time?	
Fix: Retry with backoff, then move to a DLQ or mark FAILED.

7.Why not 2PC?	
Fix: Too complex and not scalable for modern microservices; Outbox provides reliable eventual consistency.

Drawback:The Outbox Pattern introduces eventual consistency because events are published asynchronously. It also requires an additional Outbox table, a background publisher service, retry logic, monitoring for stuck events, and idempotent consumers to handle duplicate deliveries.
