Google Drive System design/Backup File System/dropbox:

functional requirements:
-> Are we building personal cloud storage?
->User can upload and download files
->File Sharing with link
->millions of concurrent users
->file size can go upto 5gb
->folder hierarchy
->file versioning

non functional requirements:
->Secure
->Scalable
->durable
->like we said lot of concurrent users should be handled
->eventual consistency across metadata replication
->Highly Available
->low-latency

Estimate:
100M users
10M DAU[daily active users]
Average size per user allowed-> 20gb
then storage needed 2EB+

Average uploads per day-> 50M files/day
average size of file~->10MB 500TB uploads/day should be how our estimation calculated.

Metadata
-> We never store original files or objects in db.
user-> userid,user_name,email,quota
file->file_id,file_name,size,mimeType,storagePath,checkSum(validation),currentVersion,createdAt
fileversion->versionId, file_id, size, storagePath,createdAt and checkSum(validation).
sharing-> sharing_id,file_id,permisions,expiry,share_to
folder structure-> folder_id,ownerId,parent_id,name

Uploads and Downloads Flow:

user-> API -> authenticated-> generate file_id-> metadata DB->generate presigned url upload-> client directly uploads to url-> successful callback-> metadata update

user-> API->metadata DB -> storagepath-> generate download url-> object storage-> client downloads successfully

Object Storage-> since we require cheap,scalable, durable, able to handle concurrent users and large size files[multipart uploads] better to have object storage instead of maintain other db so we can go with s3/gcs and azure blob-> for every object=> user_id/file_id/version

metadata db-> use postgresSQL[heavy read workflow is it like wal based or durable guarantee ACID] or if MySQL add indexes(owner_id,file_id and parent_folder).

redis added-> for user metadata
	-> for frequently downloaded files
	-> sharing permissions 
	->folder structure

Popular files to be served with help of CDN
client-> CDN-> object storage


for large file uploads-> divide the files into chunks chunk1,chunk2,... and upload independently
	benefits: parallel uploads
		->retry only failed chunks
		->resume uploads {with support of upload session state}

deduplication can be prevented using file hash(SHA-256) if already present/key exists then reuse storage else store file.

versioning important-> maintain different versions v1,v2,v3 even though we make sure metadata points to latest version preserve old versions too.

sharing-> db-> token, expiry, permission 
	-> Generate random UUID urls
	validate before downloading

search only metadata-> use indexes(file_name,owner_id,tags,folder_name)
 or add elasticssearch/opensearch for full text search

Background jobs-> after upload
	-> message queues[kafka/rabbitmq]-> virus scan-> thumbnail generation- OCR-> notification-> indexes search 
	-> don't stop or pause upload responses

Fault tolerance: replication 3 copies can be one per region 
	-> metadata primary-> replicas[automatic fault tolerance]

security concerns: encryption at rest/transit
-> access tokens
-> signed url prevent unauthoritive stuffs
->token with expiry
-> checksum validation 


BottleNecks:
upload server slow or too much traffic
solution:direct upload to object storage

metadataDB:
millions of request -> try redis/read replicas/data sharding

storage-> huge data -> break into chunks-> distributed object storage

Scaling scenarios:
->Stateless service behind LBs.
-> horizontal scaling-> lb-> auto scaling
-> metadata Primary-> replicas-> partitioning
->Storage-> Object Storage-> CDNs


APIs: get{donwload/{id}}
	post{upload/file json body structure}
	delete{file/{id}}
	put{rename}
